# **1. Go: что повторить перед началом**

Обязательно освежить

Не нужно одинаково глубоко повторять все возможности языка. Я бы расставил приоритеты следующим образом.

### **1.1. Основы языка**

Пройдись по следующим темам:

| Тема          | Что вспомнить                                        |
| ------------- | ---------------------------------------------------- |
| Типы данных   | Строки, числа, bool, массивы                         |
| Struct        | Создание структур, композиция                        |
| Pointers      | Указатели, передача по значению и ссылке             |
| Slices и Maps | Работа с коллекциями                                 |
| Functions     | Функции, variadic, multiple return                   |
| Methods       | Методы, pointer/value receivers                      |
| Interfaces    | Интерфейсы, реализация, композиция                   |
| Errors        | Обработка ошибок, wrapping, `errors.Is`, `errors.As` |
| Defer         | Отложенное выполнение                                |
| Packages      | Пакеты, экспортируемые имена                         |
| Generics      | Общее понимание параметров типов                     |

Особенно внимательно повтори **interfaces, pointers, structs и errors**. Они будут постоянно встречаться при проектировании серверной архитектуры.

Generics достаточно понимать на базовом уровне. Строить на них архитектуру Gornet нет необходимости.

### **1.2. Конкурентность**

Особенно важно

Это одна из наиболее важных частей Go для твоего проекта.

Пройди:

- Goroutines.
- Channels: buffered и unbuffered.
- `select`.
- `sync.Mutex` и `sync.RWMutex`.
- `sync.WaitGroup`.
- `sync.Once`.
- Race conditions.
- Graceful shutdown.
- Context cancellation.

Почему это важно:

Gornet будет одновременно обрабатывать запросы разных клиентов, выполнять операции модулей и потенциально запускать длительные задачи.

Например, несколько пользователей могут одновременно запросить информацию о сервере или запустить разные операции.

Тебе важно понимать, как синхронизировать доступ к общим данным, корректно завершать горутины и не допускать утечек ресурсов.

Отдельно изучи пакет `context`: передача контекста между функциями, отмена операций, таймауты и дедлайны. Это фундаментальная часть как Go-backend, так и gRPC.&#x20;

# **2. RPC и gRPC: новая для тебя область**

Обязательно изучить перед разработкой API

Здесь я бы не ограничивался пониманием того, как вызвать удалённый метод. Нужно разобраться в общей модели взаимодействия.

### **2.1. Теория RPC**

Сначала изучи:

- Что такое Remote Procedure Call.
- Client-server взаимодействие.
- Service и Method.
- Request и Response.
- Сериализация и десериализация.
- Stub / Client.
- Unary RPC.
- Server Streaming.
- Client Streaming.
- Bidirectional Streaming.

Последние три вида streaming достаточно понимать концептуально. Для начала Gornet будет достаточно Unary RPC.

### **2.2. Protocol Buffers**

Это самостоятельная часть, которую обязательно нужно освоить.

Пройди:

- Что такое `.proto`.
- Синтаксис proto3.
- `message`.
- `service`.
- `rpc`.
- Типы полей.
- `enum`.
- `repeated`.
- `optional`.
- Вложенные сообщения.
- Нумерация полей.
- Генерация Go-кода из `.proto`.

Особенно важно понять версионирование контрактов.

Например, номера полей Protobuf нельзя произвольно менять или повторно использовать после удаления: это может привести к несовместимости и неправильной интерпретации данных. Удалённые номера следует резервировать.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://protobuf.dev\&sz=32)

Protocol Buffers Documentation+1



### **2.3. gRPC на Go**

После теории Protocol Buffers переходи к реализации.

Тебе нужно понимать:

1. Создание gRPC Server.
2. Регистрация сервисов.
3. Реализация RPC-методов.
4. Создание gRPC Client.
5. Вызов удалённых методов.
6. Передача данных.
7. Обработка ошибок.
8. Передача Metadata.
9. Deadline и Timeout.
10. Interceptors.
11. TLS.

Особое внимание удели двум вещам:

**Interceptors** — механизм, который позволит реализовать общую обработку запросов: аутентификацию, авторизацию, аудит и логирование без копирования одинакового кода в каждый RPC-метод.

**Deadlines и Cancellation** — механизмы, позволяющие ограничивать время выполнения запроса и корректно прекращать работу, когда клиент отменил операцию.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://grpc.io\&sz=32)

Streaming, Health Checking и Graceful Shutdown изучи на начальном уровне, но детально реализовывать их до возникновения необходимости не нужно.

# **3. Архитектура backend-приложений**

Обязательно изучить на концептуальном уровне

На мой взгляд, это не менее важно, чем сам Go.

Не нужно изучать Clean Architecture наизусть или пытаться сразу реализовать все известные архитектурные паттерны. Но некоторые принципы тебе понадобятся.

### **3.1. Разделение ответственности**

Разберись с назначением следующих слоёв:

- Transport Layer — приём и обработка RPC-запросов.
- Application Layer — выполнение сценариев и бизнес-логики.
- Infrastructure Layer — работа с ОС, БД и внешними API.
- Domain Layer — предметные модели и правила, если они действительно нужны.

Например:

```
gRPC Request
     |
     v
Transport
     |
     v
Application Service
     |
     v
Infrastructure
     |
     v
Operating System
```

Важно понимать, почему сетевой обработчик не должен самостоятельно выполнять всю бизнес-логику.

### **3.2. Модульная архитектура**

Для Gornet это фундаментальная тема.

Изучи:

- Separation of Concerns.
- Dependency Injection.
- Dependency Inversion.
- Интерфейсы как контракты между компонентами.
- Composition over Inheritance.
- Модульный монолит.
- Регистрация компонентов.
- Жизненный цикл модулей.

Тебе не нужно строить полноценный plugin framework. Достаточно понять, как Server регистрирует статически подключённые модули и их gRPC-сервисы, а CLI — соответствующие команды.

### **3.3. Многосерверная архитектура**

Поскольку ты планируешь размещать несколько независимых экземпляров Server, изучи:

- Stateless и Stateful компоненты.
- Независимые конфигурации экземпляров.
- Управление несколькими подключениями.
- Изоляцию состояния.
- Обнаружение возможностей сервера.
- Совместимость версий клиента и сервера.

При этом тебе пока не нужна теория построения Kubernetes-кластеров, распределённых баз и микросервисных систем. Твоя текущая модель — несколько независимых серверов, которыми управляет один CLI.

# **4. Безопасность**

Изучить основы до реализации аутентификации

Для Gornet безопасность особенно важна, поскольку Server будет предоставлять удалённый доступ к системным операциям и внешним сервисам.

Я бы изучил следующие понятия:

| Тема               | Что нужно понять             |
| ------------------ | ---------------------------- |
| Authentication     | Как определить клиента       |
| Authorization      | Какие операции ему разрешены |
| TLS                | Защита сетевого соединения   |
| Access Tokens      | Аутентификация запросов      |
| RBAC / Permissions | Разграничение полномочий     |
| Least Privilege    | Минимально необходимые права |
| Secret Management  | Безопасное хранение секретов |
| Audit Logging      | Регистрация действий         |
| Rate Limiting      | Ограничение частоты запросов |

Есть принципиально важный момент: нельзя надёжно гарантировать, что запрос пришёл именно из твоего официального CLI. Другую программу можно написать с теми же RPC-контрактами.

Поэтому Server должен доверять подтверждённым учётным данным и разрешениям, а не факту использования конкретного бинарника.

На начальном этапе достаточно хорошо понимать TLS, токены и различия между Authentication и Authorization. Конкретную реализацию можно изучить при разработке Core.

# **5. Дополнительные направления, которые понадобятся во время разработки**

Здесь уже не рекомендую заранее проходить полноценные курсы. Достаточно знать, что именно придётся изучить.

| Направление         | Что изучать                                 | Когда пригодится                |
| ------------------- | ------------------------------------------- | ------------------------------- |
| CLI Development     | Аргументы, флаги, команды, конфигурация     | При создании CLI                |
| Linux API           | `/proc`, `/sys`, systemd, системные вызовы  | Host Module                     |
| HTTP Client         | HTTP, REST, JSON, авторизация, пагинация    | GitHub Module                   |
| SQLite              | SQL, таблицы, индексы, транзакции           | Хранение состояния              |
| Database Migrations | Изменение схемы БД                          | При развитии Core               |
| Async Jobs          | Очереди, статусы, отмена, повторные попытки | Backup и другие долгие операции |
| Observability       | Логи, метрики, диагностика                  | При стабилизации Server         |
| CI/CD               | Тестирование, сборка, релизы                | При публикации Gornet           |

Особенно важно понимать, что gRPC между CLI и Gornet Server не запрещает использовать REST внутри отдельных модулей.

Например:

```
CLI
 |
 | gRPC
 v
Gornet Server
 |
 ├── Host Module
 │      └── Linux API
 │
 └── GitHub Module
        └── GitHub REST API
```

Это совершенно нормальная архитектура: транспорт твоей платформы и протоколы сторонних систем — независимые вещи.

# **6. Практическая подготовка перед Gornet**

Я бы не переходил сразу от чтения теории к разработке полноценной платформы. Сделай небольшой технический эксперимент, который проверит основные знания.

## **Подготовительный мини-проект**

Go + gRPC + Protobuf

**Цель:** реализовать простейшее клиент-серверное приложение, которое получает системную информацию.

1. **Создать Protobuf-контракт**

   Описать `HostService` с методом `GetInfo`.
2. **Сгенерировать Go-код**

   Установить `protoc` и генераторы Go и gRPC.
3. **Создать Server**

   Реализовать gRPC-сервер, который возвращает информацию об ОС.
4. **Создать Client**

   Отдельная CLI-программа вызывает `GetInfo` и выводит результат.
5. **Добавить обработку ошибок**

   Проверить недоступность сервера, некорректные запросы, таймауты.
6. **Добавить защиту**

   Настроить TLS и простую аутентификацию через токен.

Это не первый модуль Gornet, а отдельный эксперимент. Не стоит заранее превращать его в часть основного репозитория.

Когда сможешь самостоятельно написать такой проект, понимать каждый компонент и объяснить, как запрос проходит от CLI до Server и обратно, можно переходить к разработке Gornet.

Для первого знакомства с инструментами официальная документация предлагает именно такую последовательность: описание `.proto`, генерация клиентского и серверного кода, реализация клиента и сервера.&#x20;
